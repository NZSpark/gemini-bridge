## 4. 载体改造（10-07）：工具调用为什么要「标记行 + 围栏」

**动因**：纯文本 `TOOL_CALL: {json}` 一行会被网页版当 markdown **段落**渲染，`\"` 转义被消费 →
取回的文本不再是合法 JSON，解析只能靠修复启发式**猜**。

**探测方法（值得照抄）**：4 臂 A/B（纯文本行 / 只用围栏 / 标记行+围栏 / ```python 对照），
任务是**运输层回声**（让模型逐字节搬运给定 payload，只测渲染层），
请求**不带 `tools`**（否则桥自己的格式指令会污染实验）。结果固化成单测样本 + `doc/code_block_fence.md`。

**真机结论**：

| 载体 | 保真 | 渲染后可识别 | 结论 |
| --- | --- | --- | --- |
| 纯文本行 | ❌ 转义被吃 | ✅ | 弃用 |
| 只用 ` ```tool_call ` 围栏 | ✅ | ❌（DOM 里只剩 `Code snippet`，围栏与 info string 都不进 `innerText`） | 在 Gemini 上不可用（解析 0 条） |
| **标记行 `TOOL_CALL:` + 围栏** | ✅ | ✅ | 采用 |

**教训**：「可识别」与「保真」必须由**两个部件**分别承担；载体必须真机验证，
不能拿别的站点的结论照搬（照搬「只用围栏」在 Gemini 上直接失效）。

## 5. 输入框战争（10-07）：五轮连败到全胜

这是整个项目最贵的部分。五轮里每一轮的「第一解释」都曾被真机推翻；记录下来比结论更重要。

### R1 失效句柄（T11.2）
- 现象：写入报 `waiting for element to be visible, enabled and editable`，客户端重试同样失败。
- 初判：输入框不可见。
- 真因：旧实现「定位一次句柄 → 一次 fill」，重挂载后句柄永久失效；30s 超时把窗口耗光。
- 修法：每次尝试**重新定位** + `FILL_TIMEOUT_MS` / `FILL_RETRIES` + 失败诊断（元素状态快照）。
- 证据：换回旧代码，4 个新用例变红。

### R2 长度控制核查（T11.3）
- 用户报告：长 prompt 导致网页失去响应，长度控制「没生效」。
- 先证伪：控制**没有被绕过**（全仓只有一处 fill；四个预算旋钮都真的被读到）；失效的是
  **计量口径与可观测性**——单条预算没有总量、播种只计原始文本、兜底截断完全静默。
- 真机实测：20K / 60K / 100K prompt 全部正常收发 → **`PROMPT_MAX_CHARS` 是主动预算，不是物理上限**。
- 修法（纯可观测性，零保真风险）：截断必记 WARNING；每次发送记 prompt 长度；
  超时报错里带长度。

### R3 提交链失效（T11.4）
- 现象：文字已在输入框里，但消息没发出去，客户端干等超时。
- 真因：`_dispatch_enter` 的 JS 只要把合成 `KeyboardEvent` 派发出去就 `return true`，
  旧 `_submit_prompt` 据此**直接返回**——发送按钮兜底路径**从未执行过**。
- 修法：阶梯「Enter → 发送按钮 → Enter」，每级用 `_prompt_submitted` 验证
  （**输入框已清空**或页面进入生成中）；新增 `SUBMIT_VERIFY_MS`；
  发送按钮先原生 `click()`（真实鼠标事件）再退 DOM click。
- 同轮落地预算策略：超长工具结果**不整块丢**，只留开头 + 标注「已截断 N 字符」；
  拼装后成品超预算时按「最长优先砍半」压缩到下限。

### R4 超长结果卡死主线程（T11.5）
- 现象：几万字符的 prompt 一到网页，输入框整个卡死。
- 真因：一次性 `fill(整段)` 把渲染排成网页主线程上的**长任务**；Playwright 探测不到元素状态。
- 修法：分块写入（`FILL_CHUNK_CHARS=4000`）；每块前**重读输入框文本只补缺失段**（幂等、可续写）；
  每块之间 `await asyncio.sleep(0)`；「已写入字符数不前进」连续 N 次抛错；
  读不到文本的页面回退整段 fill。

### R5 合并 ChatGPTBridge 原语（T11.6）
- 对比结论：对方**插入/聚焦/清空/提交原语更强**（真实键盘 Enter、原生 click、循环校验清空草稿），
  本项目**分块与双重校验更强**。
- 合并：`_focus_composer`（真实 click 优先）、`_clear_composer`（多手法 + 循环校验）、
  `_keyboard_enter`（真实键盘 Enter 首选）——**合成事件 `isTrusted=false`，受控编辑器会直接忽略**。

### R6 零字符静默空操作（T11.7）
- 现象：prompt 只有 9.6K，三次尝试全部「已写入 0/9633 字符」；日志里**没有任何原语失败行**
  （DEBUG 开着）——原语「成功」了，但输入框没变。
- 真因（读 Playwright 源码证实）：`keyboard.insert_text` 与 `execCommand('insertText')`
  **都只在当前选区处插入**；输入框已是 `activeElement` 时 `focus()` 是空操作 → 没有选区 →
  静默空操作。对照 `fill()`：它是「selectText 建立选区 → insertText」的复合动作，所以一直可用。
- 修法：插入前**显式放置光标**（focus + `selectNodeContents` + 折叠到末尾，与 fill 同源）；
  零进展时记 warning（含 `caret_in_composer` 诊断）并**回退整段 fill**。
- 元教训：**缺失的日志行本身是证据**——「该报错的地方没报错」比错误信息更有指向性。

### R7 自我毁灭循环（T11.8）
- 现象：36.5K prompt，光标诊断 `caret_in_composer: true` 仍然「已写入 0」；
  但同请求另一次诊断 `child_nodes=616`（整条 prompt 明明已渲染）。
- 真因：编辑器把**每条换行渲染成独立块级节点**，读回 `textContent` **不含换行**；
  续写判据 `prompt.startswith(current)` 对多行文本永远为假 → 触发「清空重写」→
  写进去又被自己清掉，`child_nodes` 616→1 逐轮塌缩。
- 修法：`_normalize_for_compare`（空白折成空格）+ 容错判据；进入清空分支**之前**先检查
  「已在框里就当写完」，**绝不清掉已写好的内容**；`fill()` 提到首位。
- 元教训：**先检查测量工具本身**。三轮排查都在查「写不写得进去」，没人查
  「我们用来判断写没写进去的那把尺子」。

### R8 回归：校验否决了成功（T11.9）
- 现象：R7 之后第一轮，`fill` 成功但读回少 133 字符 → 判死 → 分块 → 清空 → 彻底失败。
- 真因：读回是**有损**的（换行/标记渲染损耗），把校验判据放到了**成功路径**上。
- 修法：`fill()` 没报错就**信任它**（差异只记 INFO）；只有 `fill()` 报错时才读回救援
  （真机见过报超时但文本已落地）。
- 元教训：**校验只能用于发现失败，不能用于否决成功**。

### R9 日志误读（T11.10）
- 现象：用户看到「播种内容超出预算」就以为本轮发了播种 prompt。
- 真相：`server.py` / `responses.py` **每轮无条件构建两份 prompt**（增量 + 播种），
  由 `needs_seed()` 决定发哪份；那一行是**构建期**日志，不说明发送行为。
- 修法：发送日志标注**本轮实际发出**的版本：`[发送] bucket=X 用{播种|增量} prompt=N 字符`，
  且标注变量与实际选择是同一个。

**测试基线**在这一天从 303 涨到 341，全部不联网；每一轮都有区分力实验记录。

## 6. 结束判定加固（10-08）：旧内容 / 回显绝不能当回复

- 现象：每 14~15 秒一轮 `200 OK`、prompt 恒为 7126 字符、无限重复；没有一条 WARNING——
  桥每轮都自认为成功。用户判断：**网页端失去响应，但桥把「指令」交回客户端，提示词反复叠加**。
- 两条判据同时失守：
  1. 发送前基线取 `nodes[-1]`，轮询取「最后一个**有正文**的节点」——不响应时基线成空串，
     轮询回退读到**上一轮的旧回复**（很可能正是上次的工具调用指令）；
  2. 所有收尾路径都不要求内容更新；`stalled` 还用 `normalized or …` 复位——页面上留着旧回复就永不失败。
- 修法：`_latest_reply`（基线与轮询**同一口径**）；`_text_fingerprint` / `_looks_like_prompt_echo`
  （去空白比较 + 前 120 字符 + 长度比，容忍有损渲染）；`text_is_new` 成为**所有**收尾路径的硬条件；
  无新正文连续 2 轮即 `pending_rotation` + 超时 → 重试阶梯会**重开对话 + 重新播种**。
- 取舍：**宁可失败，也不返回旧内容**（模型恰好逐字回复旧答案的罕见情形会多跑一轮重试，
  但绝不再把上一轮的指令交给客户端）。
- 验收：4 个新用例；换回旧代码全部变红；完整套 346 passed。

## 7. 页面生命周期（10-09）：死页面不许永久 502

- 现象：OpenAI SDK 调用 502「无法找到对话输入框」；`/v1/models` 正常；
  同一请求换桶（`default` / 新桶）返回 200；对坏桶 `POST /session/reset` 报
  `Target page, context or browser has been closed` —— 决定性证据：**桶里的页面早已被关闭**。
- 根因：`_ensure_page` 只看 `bucket in self._pages`，从不检查 `page.is_closed()`；
  死页面上的 `wait_for_selector` 抛错被 `except Exception: continue` 吞掉，
  最终误报「未登录 / 找不到输入框」，该桶永久 502。
- 修法：`_page_closed` 探活；死句柄**摘除 + 重建**并置 `has_history=False`（下一轮播种，对话不丢）；
  导航失败不把半死句柄留在池里；报错指向真因（「页面已关闭」不再说「未登录」）。
- 验收：5 个新用例；换回旧代码 3 个变红；351 passed。

## 8. 桥内命令与收尾（10-11）

- **`/bridge` 本地命令**：浏览器没起来、句柄失效时，它是唯一还能用的排障入口。
  命令在 HTTP 边缘本地应答（`/bridge status`、`models`、`session reset/reseed`、
  `settings save-files …`）；只认「整条消息就是这一行」，历史消息里的旧命令不重放，
  只作用于当前会话桶。`chat` 与 `responses` 两条路径行为一致（含流式）。
- 同轮补充 667 行命令测试；README / doc 同步；项目统计更新。
